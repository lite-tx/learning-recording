# Recording 案例

> 这些案例来自用户实际的学习日记和讨论。它们展示如何保留思考过程、如实呈现理解变化，以及写出符合用户习惯的记录。每篇日记不需要套用相同结构。

## 保留思考的来路

### LeetCode 453：从模拟到等价变换

**当时实际发生的过程**

用户最初想不断找到数组最大值，让其他 n-1 个数加一，直到所有元素相等。继续讨论后，发现这种写法需要反复维护最大值、判断数组是否相等，写起来比较麻烦。之后才把操作反过来看：每次给 n-1 个元素加一，等价于给剩下的一个元素减一，最后推到只需记录总和和最小值。

**日记中保留的写法**

> 我最开始想的是随着循环次数不断调整最大值，然后让其余的 n-1 个数加 1，直到所有元素相等。不过这样就得一直动态维护最大值，而且还要不断判断数组是否相等，这真的很麻烦。
>
> 后来发现这道题其实根本不用模拟。给 n-1 个元素加 1，可以等价看成给剩下的一个元素减 1。

这段写法保留了用户原来的想法和后来发生的变化。它没有把答案提前写进开头，也没有把整段推导改写成算法题解。

**对照写法**

> 本题通过数学推导，将时间复杂度优化至 O(n)，最终得到 total - n * min。

这句话可以作为题目摘要，但单独用它代替日记，就看不出用户如何得到这个结论。

### LeetCode 3841：把多次优化之间的联系留下来

**当时实际发生的过程**

用户最初考虑用邻接表和 BFS 找树上两点之间的路径。后来理解可以用根路径前缀异或和 LCA 处理查询。修改节点时，最初又想到 BFS 遍历子树；发现复杂度不理想后，才通过 DFS 序把子树转换成连续区间，再引入差分和树状数组。

树状数组这一段尤其重要：用户已经理解每个节点负责的区间，却不明白为什么实际查询得到的值与单个 bit[i] 不同。讨论补上了 diff 和累计 change 的关系，用户才理解树状数组维护的是修改产生的差分。

记录时应留下这些方法为什么出现、它们如何连接，以及理论与题目变量之间的对应关系。不需要逐条抄录每一次提问，也不要只列出 BFS、DFS 序、Fenwick Tree、LCA 等名词。

## 如实呈现理解变化

### LeetCode 3970：不要把后来形成的状态设计写成最初就知道

**当时实际发生的过程**

用户知道题目属于带权最短路，并提出根据当前节点和下一个节点的 label 判断连续次数的想法。后来发现，只记录到达节点的最短距离不够，因为到达同一个节点时，末尾连续相同字符的次数可能不同，后续能否继续走也会不同。讨论后才引入 dist[u][cnt]，并把状态放进 Dijkstra 的优先队列。

记录时先写最初的判断方式，再写为什么单独的 dist[u] 不够，最后写增加 cnt 维度的原因。环路问题如果是用户后来提出的，也应保留它出现的位置。

**不应写成**

> 用户一开始就意识到需要二维 dist 数组，并熟练使用 Dijkstra 解决带约束最短路。

这会把讨论后形成的认识提前归给用户，也夸大了最初的掌握程度。

## 写成用户自己的笔记

453 的日记使用第一人称，从「今天做了 453」自然讲到最初的想法、遇到的麻烦和后来发现的操作转换，最后写下「没想到这道题居然是这样做出来的」。

写新的日记时，可以参考它的叙述方式，但不需要每篇都复用同样的开头或结尾。用户的自然表达会随话题变化；模仿的是整体的直接程度、叙述节奏和思考路径，不是复制某几个口头禅。

**对照写法**

> 本次学习充分体现了算法思维的深度与广度，最值得记住的是从表象走向本质的思想跃迁。

这种拔高式总结不符合用户平时的表达方式。

## 按需要保存成果

453 的现有日记把模拟方案和等价变换放在正文，完整 C++ 代码放在「当时的代码」折叠区域。这样的安排让正文仍然围绕思考过程展开，同时保留了以后查阅代码的入口。

如果用户只要求一份草稿，就先给草稿；只有用户明确要求写入 Notion 时，才执行保存。不要把“草稿已生成”和“页面已成功写入”混为一谈。
