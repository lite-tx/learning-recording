# 设计实验记录

> 本文件用来记录可观察行为与我们从中得出的假设。不要把案例回放当作有控制条件的实验。

## 试验 001 — C++ vector 扩容与 reserve

- **测试目的**：在用户已经知道主要原理时，是否能避免不必要的基础复述，并发现具体知识偏差。
- **实际情况**：用户正确解释 `push_back` 可能因扩容使指针失效；在继续讨论 `reserve` 时，误记了它对容量与内存重新分配的影响。
- **观察**：从已知概念出发的示例说明有效；但主动追加问题可能超出用户当时的学习目标。
- **后续**：需要在新场景中比较「继续追问」与「按用户指示结束」的适用条件。

## 试验 002 — C++ 伪共享（Learning 第二次测试）

- **测试目的**：在用户对知识点不熟悉时，能否接着现有直觉一起推导，而不要求用户猜测尚未解释的新术语。
- **用户最初的想法**：软件层面的原子操作没有数据竞争，性能影响可能来自硬件；后来联想到缓存换入换出以及循环遍历顺序的局部性。
- **出现的障碍**：AI 先提出了「两个核心能否独立维护同一条缓存行」的问题，但未说明「维护」指的是缓存一致性中的写权限与失效等动作。用户明确说不理解这个问题的表述。
- **后续解释**：AI 补充缓存行所有权在不同核心间争用的机制，同时区分它和普通内存访问局部性的差异。
- **回放观察**：从用户已经提出的硬件方向继续讲解是合适的；不应通过含糊的新术语强行制造一道推导题。是否充分掌握该知识点没有经过独立验证。
- **候选改进**：当用户指出一个新术语或动作指代不清时，优先补足具体对象、动作与已有理解的关系，不要求用户先给出长篇解释。

## 试验 003 — 临时任务结束后恢复学习主线

- **原来的主线**：正在进行 Learning v0.1 的第二次测试，学习 C++ 伪共享，尚未复盘。
- **用户主动开启的分支**：决定把 Learning & Recording 放进 GitHub，创建公开仓库并修改 README。
- **实际发生的情况**：仓库和 README 处理完成后，没有立刻指明原来的测试尚未复盘。用户随后问「那我们接下来要做什么？这刚好又是一个案例，我好像忘记我们原本要做什么了」，AI 才整理原主线与分支。
- **回放观察**：主动切换任务完全合理；但分支完成时，可以用一句话保留未完成主线的恢复入口，由用户决定是否返回。
- **候选改进**：不强制回到原任务，也不要求用户自己记下任务栈。完成临时任务后，在确有未完成主线时简短指出它。
- **验证限制**：这是一次已经发生的恢复案例，不足以证明所有长对话都应采用同样的提醒方式。

## 试验 004 — Recording：伪共享学习过程的日记草稿

- **测试材料**：伪共享学习中的真实对话，以及中途转去创建 GitHub 仓库、之后恢复主线的经历。
- **草稿处理**：使用第一人称记录从软件层面怀疑硬件问题、对缓存行表述感到困惑、尝试用缓存换入换出来解释，再到获得缓存一致性解释和转去处理仓库的经过。没有把后来的解释写成用户已经独立掌握的结论。
- **用户反馈**：认为这份文字「在这个范围内模仿到我的精髓」，其余场景等实际遇到再提出修改；认为提前强行测试文风不一定能发现问题。
- **暂时结论**：这份草稿在当前范围内符合预期，不据此认定已掌握所有场景的个人文风。Recording 先保留现有方式，后续以真实使用中的具体反馈调整，不特意制造额外的文风测试。
- **状态**：草稿已获正面反馈，尚未写入 Notion；这条记录只描述本次测试，不代表正式插件已经完成。
