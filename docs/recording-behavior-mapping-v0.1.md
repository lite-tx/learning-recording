# Recording 行为映射 v0.1

> 这份文件位于 Recording 的思想设计与 Skill 指令之间，用来把已经确认的记录原则转换成可观察的行为。它是设计参考，不是每次记录都必须按顺序执行的流程。

## 记录真实的思维变化

**什么时候会遇到**

- 用户明确要求整理一次学习经历、写学习日记或保存某段推导。
- 一次学习中出现了有意义的思路变化、关键障碍或理解转折。
- 用户只想保存某个具体结论、代码或资料，而不是完整日记。

**AI 应该怎么做**

- 先确认本次要记录的范围和用途，再回顾当前对话及相关历史资料。
- 找出对理解有帮助的节点：最初的想法或已有认识、遇到的问题、出现矛盾的地方、推动理解变化的推导，以及这些变化如何连接到最后的结论。
- 按照思维关系组织内容。必要时保留时间顺序，但不为了复述聊天而逐条罗列消息。
- 只记录与本次目标有关的内容。一次学习如果没有值得整理的过程，也可以只保存用户指定的资料或简短结论。

**AI 不应该怎么做**

- 把整段聊天按时间顺序改写成流水账。
- 只留下最终答案，删掉用户如何走到答案的过程。
- 为了让日记看起来完整，补充对理解没有帮助的寒暄、重复解释或无关分支。

**对应案例**

- LeetCode 453：保留用户从“反复找最大值、给其他元素加一”的模拟想法，经过操作成本和等价变换，最后得到总和与最小值公式的过程。
- LeetCode 3841：保留从 BFS 第一版，到 DFS 序、差分、树状数组和 LCA 的思路变化，尤其是理论与实际变量终于对应起来的那段推导。

## 忠实区分想法、解释和结论

**什么时候会遇到**

- 对话中用户提出了猜测，AI 随后提供解释。
- 用户经过讨论表示理解，但理解范围可能只覆盖某个具体问题。
- 最终代码、指标或结论是否由用户实际验证尚不明确。

**AI 应该怎么做**

- 区分用户最初提出的想法、AI 提供的解释，以及双方经过讨论后确认的结论。
- 记录用户当时真实表达的理解程度。用户说“这里明白了”，只说明当时讨论的具体内容得到理解，不自动扩大成已经掌握整个知识领域。
- 区分猜测、暂时接受的解释、经过推导确认的结论，以及实际运行或测试验证过的结果。
- 对代码来源和完成状态保持准确。如果只能根据讨论整理代码，就明确标注“根据讨论整理”，不要称为用户最终提交版本。
- 如果无法确认某个事实，就省略、标注不确定，或向用户核实，不用合理猜测填补空白。

**AI 不应该怎么做**

- 把 AI 刚讲过的内容写成用户一开始就知道的知识。
- 把用户的一句“明白了”扩大成全面掌握或能够独立应用。
- 编造用户没有表达过的心理活动、困难、感受、成绩、测试结果或最终代码。
- 把推测写成已经验证的事实。

**对应案例**

- LeetCode 3841：用户最初理解树状数组的区间覆盖，但不理解它如何用于子树修改。日记应记录后来通过差分数组和前缀查询补上了这层联系，不能把 AI 最初的解释直接算作用户已经掌握的内容。
- LeetCode 3970：用户最初提出状态转移想法，之后才理解为什么最短路需要增加“末尾连续相同字符数量”这一维。记录时要保留这个认识变化，不要把最终状态设计写成一开始就想到了。

## 区分日记正文和附属资料

**什么时候会遇到**

- 一次学习既有值得记录的思考过程，也有完整代码、公式、图表或资料链接。
- 用户希望以后能回看最终成果，但不希望正文变成技术讲义。

**AI 应该怎么做**

- 正文以第一人称的学习过程为主，连贯记录想法、问题、推导和认识变化。
- 完整代码、公式、图表、论文或参考链接等放在附属区域，按需保留。
- 附属资料应与正文中的讨论对应，方便以后查阅；正文不需要重复粘贴整份代码。
- 如果某项资料对理解过程不可或缺，可以在正文中解释它的作用，再把完整内容放到附属区域。

**AI 不应该怎么做**

- 让完整代码或资料占据正文主体，挤掉思考过程。
- 为了追求简洁而丢弃用户明确希望保留的最终成果。
- 每篇记录都强行附上代码、公式或链接。

**对应案例**

- LeetCode 453：正文保留从模拟到等价变换的思考过程，完整 C++ 代码放在“当时的代码”折叠区域。
- LeetCode 3841：正文记录 DFS 序、差分、树状数组和 LCA 的理解过程，最终代码放在独立折叠区域。

## 默认采用用户自己的表达习惯

**什么时候会遇到**

- 用户要求撰写日记、学习总结或其他以用户本人为叙述者的记录。
- 用户对某种表达提出修改，且明确说明这是稳定的个人习惯。
- 需要判断真实写作样本与临时规则草稿哪个更能代表用户。

**AI 应该怎么做**

- 替用户写个人记录时，默认采用用户自己的表达习惯，不把个人文风当成可有可无的装饰。
- 优先参考真实的 Notion 日记和当前可用的用户对话。日记能展示较完整的书面表达，对话能补充自然口语、思考方式和临场措辞。
- 写作前根据本次内容选择相关样本，不需要每次读取整个知识库。不同领域或不同用途的文字可以有差异，不把某一篇日记当成所有场景的唯一模板。
- 保留用户自然、平铺直叙的表达，允许出现真实的疑惑、惊讶和转折。避免机械套用 AI 常见的拔高句式或对比结构。
- 用户明确指出某种表达不符合习惯时，先修改当前记录；如果用户明确表示这是长期偏好，就用于后续同类记录。
- 如果样本不足，依据当前对话和用户明确反馈写作，不虚构用户的风格特征。

**AI 不应该怎么做**

- 把文风模仿交给某个外部插件，自己不检查写出来的文字是否符合样本。
- 只模仿表面词语，却忽略句子长度、叙述顺序、直接程度和思考过程。
- 把 AI 自己的讲解口吻写成用户的第一人称日记。
- 因为某个样本中出现过一句话，就认定它是用户长期惯用表达。

**当前可用的真实样本**

- Notion 算法日记首页及其中的 453、3841、3970、3665 等日记。
- 当前及可访问的历史 ChatGPT 对话。
- 用户在对话中明确确认的长期表达偏好。

**临时页面说明**

Notion 中名为“算法日记｜写作风格与工作流规则”的页面，是用户在提出相关问题时创建的临时草稿，不是正式规范，也不应作为权威来源。已经由用户在对话中明确确认的偏好仍然有效，但应以真实日记和对话为主要文风样本。等正式 Recording 规则完成迁移后，再按用户计划移除该临时页面；本阶段不删除它。

## 根据用户要求选择记录形式和保存位置

**什么时候会遇到**

- 用户明确要求写一篇日记、整理一段学习过程或保存某个资料。
- 用户要求直接写入 Notion。
- 用户只想先看草稿，或当前没有明确要求保存到外部平台。

**AI 应该怎么做**

- Recording 由用户主动调用或明确提出记录需求触发，不在每次 Learning 结束后自动生成日记。
- 用户只要求草稿时，先给出完整草稿，不擅自写入 Notion。
- 用户明确要求写入 Notion 时，先读取目标页面及必要的现有记录，沿用已有结构和排版，再执行写入并核对结果。
- 如果记录属于算法日记，沿用现有首页组织方式：日记按题目建立子页面；正文前保留日期、题目链接和简短题意；完整代码放在折叠区域。日期以开始思考的日期为主，跨天完成时在正文注明完成日期。
- 其他领域的记录根据实际用途选择形式，不把算法日记的结构强加给所有内容。
- 如果写入工具不可用，提供可以复制的完整草稿，并说明尚未写入；不要声称已经保存。

**AI 不应该怎么做**

- 每次学习结束后自动写日记或自动更新 Notion。
- 未经要求就创建页面、移动内容或重构已有笔记。
- 没有检查目标页面就覆盖或改变其现有结构。
- 写入失败后仍声称成功。

## 让用户反馈改善后续记录

**什么时候会遇到**

- 用户指出当前日记某句话、某段结构或某项资料不符合要求。
- 用户明确表示某种修改反映了长期的表达习惯。
- 多次实际使用暴露出相同问题，可能值得调整 Recording Skill。

**AI 应该怎么做**

- 先修正当前记录中被指出的部分，不把一次局部修改扩大成全面重写。
- 区分针对当前文章的修改与可以复用的长期偏好。只有用户明确确认或反复表现出稳定偏好时，才应用到后续同类记录。
- 如果某个问题反复出现，或某个处理方式具有代表性，可以提出将案例加入 Skill 的建议；是否修改由用户决定，并通过 Git 保留版本。
- 记录用户明确要求长期保留的偏好，但不把每次修改都自动变成 Skill 规则。

**AI 不应该怎么做**

- 每次记录完成后都强制要求用户评估。
- 因为一次改词就推断用户整体文风或性格。
- 自动修改 Skill、批量改写历史日记，或在后台持续更新规则。

## 不预设固定模板和记录任务

- 不要求每篇日记有固定篇幅、固定数量的知识点或统一小标题。
- 不要求每次学习都生成日记、口诀或总结。
- “口诀”只在出现能够跨多个题目复用的大类经验时考虑；不为每道题强行新增。
- 记录的内容、形式和保存位置由用户当次需求决定。
