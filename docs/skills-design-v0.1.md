# Learning & Recording：两项 Skill 的最小设计 v0.2

> **讨论稿。** 这份文件把我们目前认可的想法整理成将来 Skill 可以使用的行为描述。它还不是正式的 `SKILL.md`，也不代表插件已经实现。原始思想和形成过程保留在 [思想底稿](thesis-v0.md)，本文件会随着实际讨论继续修改。

## Learning

**想做的事：** 和用户一起研究当前问题，让用户能够从自己的理解出发，逐渐把问题想清楚。

- **从用户当前的理解出发。** 如果用户已经提出设想，就先沿着这个设想分析，弄清哪些部分成立、哪些地方存在问题；区分「逻辑错误」和「方法可以用但效率不高」。如果用户暂时没有思路，AI 可以先提供必要的知识、解释或示范，让双方有一个可以继续讨论的起点。双方的知识水平不必完全对等；AI 可以在需要时承担更多讲解和示范，再根据用户的理解把思考空间交还给用户。
- **灵活调整协作方式。** 双方根据当前问题和用户的需求灵活调整协作方式。AI 可以提供提示、示范、解释、质疑，也可以直接完成用户交代的工作。用户可以随时改变自己希望参与的程度。
- **共同检查理解分歧。** 讨论中出现理解对不上的地方时，结合前后的对话检查双方对概念、变量和推导步骤的理解有没有差别，也检查 AI 有没有讲错、跳步或使用含糊的表达。不要仅凭一轮交流就判断用户的想法有问题，必要时可以通过后续讨论逐渐找到原因。
- **允许分支，也保留返回主线的线索。** 学习过程中，如果解决当前问题需要先了解其他知识，可以暂时转过去。讨论时保留原来要解决的问题；当这个分支已经足以解决眼前的障碍时，帮助用户把新学到的内容接回原来的任务，再由用户决定是否继续深入。如果用户主动转向其他任务，也应该尊重新的方向。原来的任务尚未完成时，可以在新任务结束后适当提醒，帮助用户恢复之前的进度。
- **尊重学习粒度和当前状态。** 解释时要保留理解当前问题所需要的上下文和推导过程，不要为了缩短回复而省略必要的联系，也不要为了显得详细而重复已经理解的内容。学习可以深入，但要注意当前任务的范围和用户的精力状态。用户可以随时要求深入、简化、跳过或结束当前讨论。

**不预设：** 每次都要提问、复述、测试掌握程度、学习所有关联知识，或者必须遵循几个固定阶段。

## Recording

**想做的事：** 根据真实学习过程，留下未来能帮助用户重新理解的记录。

- 先看实际对话和可用资料，关注用户最初怎么理解、提出过什么设想、哪里出现了矛盾，以及通过什么推导发生了认识变化。
- 写作时忠实区分用户原话、共同得出的结论和 AI 提供的解释。没有证据的想法、心理活动或学习成果不要补写进去。
- 记录过程可以比结果更详细；最终代码、公式、资料链接等根据需要附上，不必抢占正文。避免把完整聊天转写成教学讲义。
- 记录形式由任务和用户偏好决定。必要时参考已有记录或调用可用的个人文风能力；有明确目的地时使用现有连接工具写入，没有明确写入要求时先提供草稿。
- 用户提出具体的修改意见时，先改对应记录；跨场景可复用的偏好可以在以后真正需要时整理，不强行扩展成第三个 Skill。

**不预设：** 固定的日记模板、强制总结的知识点数量、每次学习都必须产生「口诀」。

## 实现备注（不属于 Skill 正文）

- 插件由用户主动调用；这一点由插件配置负责，不需要在每轮对话中重复声明。
- 不重复实现 ChatGPT 已有的对话、推理、上下文与记忆能力。
- Notion、个人文风参考等现有能力，在具体任务需要且可用时调用。

## 接下来一起检查什么？

Learning 的主要描述已经经过几轮逐条讨论；接下来重点审查 Recording：它如何选择要记录的过程、如何区分用户的想法与 AI 的解释，以及如何让记录在未来真正帮助重新理解。

如果真实使用中出现具体问题，再修改相应句子；不为了覆盖所有理论而提前堆规则。
